A database backup in the wrong folder is one of the easiest ways to leak a WordPress site: it can contain every post, every setting, user email addresses and password hashes. During an audit of this blog I found backup files sitting in the public web folder, and one of them could be downloaded by anyone who requested its URL. This guide shows how to check your own site in a few minutes, how to block these files on an Apache or LiteSpeed server, and the Cloudflare caching trap that kept the file downloadable after I had deleted it.

Why backups end up in the web root

On shared hosting, the folder that holds WordPress (often public_html or a folder named after the domain) is the folder the web server publishes. Anything you put there, a .sql export, a .zip of the site, an old copy of wp-config.php, can be requested by URL unless the server is told to refuse it. Common causes:

  • Exporting the database from phpMyAdmin or the command line straight into the site folder.
  • Uploading a site archive to migrate it and forgetting to delete it.
  • Using Git to deploy, with the repository root being the web root, and committing backups or configuration files.
  • Renaming instead of deleting: wp-config.php.bak, backup.sql.old, site.zip.1.

That last point is what caught me. The server already refused files ending in .sql, but one dump had a name like database.sql.bak_20261113. It did not end in .sql, so the rule did not match, and the file was served to anyone.

Step 1: List what is actually in your web folder

In cPanel’s Terminal (or over SSH), go to your site folder and look for anything that is not part of WordPress:

cd ~/public_html
ls -la
find . -maxdepth 2 -type f \( -iname "*.sql*" -o -iname "*.zip" -o -iname "*.tar*" -o -iname "*.gz" -o -iname "*.bak*" -o -iname "*.old" -o -iname "*.log" -o -iname "error_log" \) -not -path "./wp-content/cache/*"

Change ~/public_html to your site’s folder. Anything this lists deserves a second look.

Step 2: Test from the outside, the way an attacker would

Seeing a file on the server does not tell you whether the public can download it. Request it over HTTPS and look at the status code. 200 means it is being served; 403 or 404 means it is not.

for f in wp-config.php backup.zip backup.sql database.sql.bak error_log readme.html .git/config; do
  printf "%-22s %s\n" "$f" "$(curl -s -o /dev/null -w '%{http_code}' https://example.com/$f)"
done

Replace example.com with your domain and add the exact names of any files Step 1 found. Test the real filenames, not just the obvious ones.

Step 3: Move backups out of the public folder (do not just delete them)

A backup is still useful; it just must not be public. Create a private folder in your home directory, outside the web root, and move the files there:

mkdir -p ~/private-backups && chmod 700 ~/private-backups
mv -n ~/public_html/*.sql* ~/public_html/*.zip ~/private-backups/
ls -la ~/private-backups/

The -n flag stops mv from overwriting a file that already exists in the destination.

Step 4: Tell the server to refuse these file types

Moving files fixes today’s problem. A server rule stops the next forgotten backup from being served. These are the rules now running on this site, added near the top of the .htaccess file in the WordPress folder. They were tested on Apache 2.4; LiteSpeed servers, common on cPanel hosting, are designed to read Apache .htaccess rules, but test after saving either way. Apache’s FilesMatch documentation explains the syntax.

# Block configuration files, backups, dumps, archives and logs
<FilesMatch "^(wp-config\.php|\.htaccess|\.user\.ini|php\.ini|error_log|readme\.html|license\.txt)$">
    Require all denied
</FilesMatch>
<FilesMatch "(\.(sql|zip|tar|tgz|7z|rar|bak|backup|old|orig|swp|log|ini|sh|env)$)|(\.(sql|tar)\.)|(\.bak[._-])">
    Require all denied
</FilesMatch>

# Never serve version-control folders, never run scripts from uploads
<IfModule mod_rewrite.c>
    RewriteEngine On
    RewriteRule (^|/)\.(git|svn)(/|$) - [R=404,L,NC]
    RewriteRule ^wp-content/uploads/.*\.(php[0-9]?|phtml|phar)$ - [F,L,NC]
</IfModule>

Notice the second rule. It matches files that end in a backup extension and also names that merely contain .sql., .tar. or .bak followed by more text. That is exactly the gap my original rule had. Test after saving: run the Step 2 loop again and make sure every sensitive file now returns 403 or 404, and that a normal page and an image still return 200.

I deliberately did not block every .gz file, because some caching plugins serve pre-compressed pages with that extension. Database dumps ending in .sql.gz are still caught by the .sql. pattern.

Step 5: The Cloudflare cache trap

After moving the files and adding the rules, my own server returned 404 for the backup archive. But requesting the same URL through the public domain still downloaded the full file. The response headers explained why:

HTTP/1.1 200 OK
Content-Length: 295905
Cache-Control: public, max-age=2592000
cf-cache-status: HIT

cf-cache-status: HIT means Cloudflare answered from its own cache without asking my server. Cloudflare’s default cache behaviour caches files by extension, and ZIP is on its default list, while HTML is not cached by default. Combined with the site’s 30-day browser-cache header, the deleted archive would have stayed downloadable for weeks.

The fix is to purge the cache: in the Cloudflare dashboard, go to Caching → Configuration and use Purge Everything (or Custom Purge for the exact URL). Then test again with the Step 2 loop. A quick way to bypass the cache while testing is to add a random query string, for example backup.zip?check=1; if that returns 404 but the plain URL returns 200, you are looking at a cached copy.

Step 6: If you deploy with Git, keep secrets out of the repository

If your web root is a Git working copy, anything committed is both served by the web server and stored in the repository history. Add a .gitignore before your first commit:

wp-config.php
*.sql
*.sql.*
*.zip
*.tar*
*.bak*
*.log
error_log

If wp-config.php is already committed, git rm --cached wp-config.php stops tracking it without deleting your local copy. Be careful on the server: the next git pull will remove a file that is no longer tracked, so copy wp-config.php somewhere safe before pulling and put it back afterwards. Removing a file from tracking does not remove it from the repository’s history; GitHub’s guide on removing sensitive data from a repository covers that, and the safest assumption is that anything once committed has been seen.

Step 7: If a backup was exposed, change the secrets

Blocking the file does not undo a download that already happened. If a database dump or wp-config.php was ever public, treat its contents as known:

  • Change the database user’s password in your hosting panel and update DB_PASSWORD in wp-config.php.
  • Replace the eight authentication keys and salts in wp-config.php with a new set from the official WordPress salt generator. This logs everyone out.
  • Change every WordPress administrator password and turn on two-factor authentication.
  • Change any API keys or SMTP passwords stored in plugin settings.

The WordPress hardening guide covers further steps such as file permissions and keeping plugins updated.

Quick checklist

  1. List non-WordPress files in the web root.
  2. Request each one over HTTPS from outside; anything returning 200 is public.
  3. Move backups to a private folder outside the web root.
  4. Add server rules that refuse backup, archive, log and config files, including names like .sql.bak.
  5. Purge your CDN cache and test again, with and without a query string.
  6. Keep wp-config.php and dumps out of Git.
  7. If anything was exposed, change the passwords and salts.
